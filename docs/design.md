# vrc-mcp-proxy — design

One owned stdio MCP proxy between the MCP client and MCP-for-Unity (pinned `mcpforunityserver==10.1.0`; upstream is not ours to patch). Server key stays `UnityMCP` in `.mcp.json`, so every `mcp__UnityMCP__*` name, doc reference, and settings matcher survives unchanged. **A behavior ships only if a named standing doc line retires with it** — the ledger below is the deliverable's measure.

## Architecture

Python/uv. The proxy spawns the pinned upstream server as a stdio subprocess and relays JSON-RPC both ways. Three layers, in order:

1. **Startup canary.** Validate upstream's tool names + schemas against the committed baseline (`canary-baseline-10.1.0.json`, 47 tools). Drift → refuse to serve the drifted tool; emit one loud error naming the bump runbook. The upstream list is **staged** — `tools/list_changed` fires when an Editor connects and custom tools register — so the canary validates the baseline subset it knows (names it shapes/allows must exist with matching schemas) rather than demanding list equality at one instant. Behaviors that key on response *strings* (console-strip) are schema-invisible — the runbook, not a runtime canary, re-validates those.
2. **Allowlist.** Tools absent from the allowlist are stripped from `tools/list` and refused on call. Never expose raw and shaped variants side by side. Resources pass through untouched.
3. **Per-tool transforms** (requests and responses), each independently disableable.

### Three standing rules for a transform

**No string keying on upstream prose, for anything that rewrites.** A transform that changes a verdict keys on structure — a `success` field, a payload shape — never on upstream's wording, because wording drifts between versions with no canary watching (`canary.py` baselines `inputSchema` only) and a key that silently stops matching turns a correction off in silence. Two carve-outs, both argued at their own rows: the venue guard keys on a marker **the proxy itself emitted** two hops earlier, not upstream prose; the compile notes key on compiler strings but only ever *append*, which is the standing `manage_gameobject_inactive_note` holds — a stale key costs the note and nothing else.

**A transform is for what the proxy can repair; a refusal is for what never reaches it.** Where upstream has already destroyed the evidence — truncated it, or discarded a return value and substituted its own verdict — no downstream transform can reconstruct it, and one that appears to have is worse than the silence. Refuse and redirect to the door that still has the truth. `read_console` (whole tool) and F22's `move`/`rename` (per-action) are the two instances.

**A transform that raises never takes the relay with it, and what the caller is told depends on the class of what failed.** Containment first, and it is not a policy choice: `pump_child` had no handler, so one raising response transform killed the relay thread — a daemon, so the process stayed alive and **mute** for the rest of the session, with later calls hanging to the client's ~1800s idle cap and the F52 watchdog left as the only thing still answering (diagnosing `execute_code` as the Roslyn hang, asserting "the editor is likely fine; other tools respond", both clauses wrong). Measured: of four calls, the client saw two. Then the policy, which is **two policies and an envelope**, not three:

- **Advisory** — a region that cannot change the verdict the caller acts on (the pin commit + `proxy_project_root`, and every note) **fails open on upstream's own raw line**. Only an annotation is lost and upstream's answer is still true; failing loud here would destroy a correct result to report a missing note. The **raw line**, not the in-flight result: `write_payload` and `add_note` mutate in place, so a region that raises midway leaves a half-rewritten response, and the loop boundary is the only place the original still exists. That is why the class rides a typed exception out to the boundary rather than being handled per site.
- **Verdict** — a region that rewrites what the caller acts on (today only the `execute_code_venue_guard` response rewrite) **fails loud**, `tool_error_result`. Forwarding the un-rewritten payload is `success:true` for a snippet that ran nowhere: the silence the no-string-keying rule above names, and the hole the F48 row's "a call nobody is checking" closed.
- **Listing** — same fail-loud policy, different envelope: a `tools/list` response has no tool result to carry text, so it refuses with a JSON-RPC error. This is the one sanctioned exception to `envelope.py`'s "a refusal is `isError`, not a JSON-RPC error", and the docstring there now says so — that rule presumes a tool call, and the alternative here is serving a tool surface the proxy could not vouch for, exposing tools it denies and skipping the canary's schema check. **Residual, stated:** a contained listing failure leaves `self.drifted` unupdated for that listing, so a client holding a cached list keeps calling tools this run never validated.
- **Request** — every request-side guard, one region, **refuses and never forwards**. A guard that raised leaves the proxy unable to say whether forwarding is safe, and every request guard exists because the unguarded forward is the dangerous arm. Ordering makes "raised ⇒ not forwarded" hold: `_write_child` is the last statement on the path.

**The class has no default; unclassified is fail-loud.** The two misclassification directions are asymmetric — advisory-as-verdict is a loud error over a correct result, visible in one round trip, while verdict-as-advisory silently reinstates the exact defect containment exists to fix. `TransformFailure` raises on an unrecognized class (a `ValueError`, not an `assert`, which `python -O` would strip), and `test_relay_containment.py` pins the whole `(region, class)` table so a region nobody classified fails a test rather than inheriting the quiet direction.

**Three invariants a containment arm must hold, and each one's absence is quiet.** They are what a mutation survives when a suite only drives the fake child, so each is pinned deliberately.

- **An arm that answers an id does `_take`'s cleanup itself** — pop `pending`, discard `timed_out`, cancel the timer — or `_watchdog_fire` finds the id still pending and writes a **second** result for it: the false Roslyn note on a call the client was already told about. The request path arms the watchdog *before* forwarding, which is where this is reachable.
- **Every write that answers the client is stderr-only on failure, never contained into an answer.** Not just the response path's last statement: the request-side refusals sit *inside* the request containment region, so a bare write there fails into the arm that then answers the same id again. A raise in a write may already have emitted the line — the reasoning that "`_write_client` is the last statement" covers failures *upstream of* the write and not failures *in* it. `_write_terminal` is the only door for an answering write; `_safe_write` is for an arm's own synthesized answer.
- **JSON-RPC ids are per-direction, so an arm answers only ids from the direction it serves.** A client line with an id and no method is the client answering a server-originated request (`roots/list`, `ping`, `sampling/*`); a relayed line with both is such a request travelling outward. Either one's id indexes the *server's* space, where `_discard_pending` would pop whichever client call shares that number and cancel its F52 watchdog — disarming an unrelated hung call, and synthesizing a reply to a request the client never sent. Reachable today on the request arm only, because every client-facing write is terminal; the response-side half is held anyway and pinned by a direct assertion.

**Not a `BEHAVIORS` entry, deliberately.** Every other behavior here is independently disableable; a safety net with an off switch is a footgun, and unlike `canary` (whose disable is the mid-bump repair path) there is no state any runbook would want it off for.

**Scope of the F52 claim:** containment removes the transform-raise *cause* of that misdiagnosis, not the misdiagnosis. `WATCHDOG_NOTE`'s "other tools respond" was always asserted rather than measured, and other relay-silence modes survive — an unresumable strict-decode failure on upstream's stream (which now takes a loud exit rather than dying quietly), a blocked `_out_lock`, a wedged upstream socket.

**Residual, stated, and not fixed here:** `write_payload`'s unprovable-shape arm leaves a would-be verdict rewrite un-applied and silent to the client ("this response was left entirely alone"). Nothing is inconsistent today — its only caller is advisory — but the first genuinely verdict-rewriting caller will need that arm to fail as loud as an exception does, or this rule will hold for a raising transform and not for a shape it declined to prove.

## Two surfaces

A tools/call result carries the payload twice: `content` (text) and `structuredContent`. 46 of the 47 baseline tools declare an `outputSchema` — `manage_camera` is the only one that doesn't — and FastMCP emits `structuredContent` for every one of them. **That is the surface an MCP client shows the model.** So a response transform writes both, via `envelope.write_payload` / `envelope.add_note`; a direct assignment into `content` is the bug below, not a shortcut.

Every response transform wrote `content` alone until this was found, so `proxy_project_root`, the `manage_asset` truth-correction (since retired for a refusal — F22's row), the `manage_gameobject` inactive note, and `timeout_notes` (on the tools that swallow a timeout — the ones that let it raise return `isError` with no `structuredContent`, and their note always arrived) reached **no caller at all** for the life of the proxy. Measured live: on a real pin, `content` carried `proxy_project_root` and the client received a payload without it; on a failed `manage_asset` delete, `content` said `success:true` with the note while `structuredContent` said `success:false` — the two halves of one response contradicting each other, with the client reading the failing one. The `tool_error_result` behaviors (allowlist, canary, `instance_guard`, F37, the venue-guard rewrite, the F52 watchdog) were never affected: they replace the whole result, which then carries no `structuredContent`, and a client skips its schema check on `isError`.

The tests passed throughout because six ad-hoc fixtures each built a result with a `content` key only — a shape upstream never sends. They now route through one builder (`tests/helpers.py`), which is the actual repair; asserting on `content` alone reproduces the original blindness exactly.

`write_payload` writes **both surfaces or neither**, and only into a shape it can prove against the pre-mutation payload: a mirror (`structuredContent` equals it) or FastMCP's wrapper (`{"result": …}`, emitted for a tool whose outputSchema carries `x-fastmcp-wrap-result` — allowlisted `refresh_unity` is one). Anything else leaves the response exactly as upstream sent it and says so on stderr, naming the behavior that declined. The all-or-nothing arm is the load-bearing part: writing `content` alone on an unprovable shape would leave a verdict rewrite reading `success:true` on one surface and `success:false` on the other, which is this section's own bug with the surfaces swapped — an un-applied correction is the status quo, a half-applied one is a lie. `add_note` is the opposite case and writes `content` regardless, because a note reaching one surface is less visible, never contradictory. Proving beats modelling upstream's serializer, since a bump can reshape it with no canary watching (`canary.py` baselines `inputSchema` only), and equality is compared over canonical JSON because Python reads `{"success": 0}` and `{"success": false}` as equal. The bump runbook's repro driver flags any call whose surfaces disagree, and any call to an outputSchema-declaring tool that returns no `structuredContent` at all — the shape a client hard-errors on. The notes' *detection* stays keyed on `content`, which upstream writes from the same value.

`add_note` needs no such proof — an added key is safe beside a wrapper — but it writes `proxy_transport_note` rather than a name a payload-writing transform would also reach for, so one response can carry both a rewrite and a note without either clobbering the other.

**Watchdog id-uniqueness boundary** (documented, not fixed): the F52 watchdog's exactly-once + late-drop guarantee is keyed purely on the client's JSON-RPC request id, so it assumes ids stay unique while in flight — true for every compliant MCP client, Claude Code included. A client that reuses an id already armed/fired collapses the two calls into one id-space: the reused id's own bookkeeping overwrites the original call's, so that call's late real response (if it ever arrives) is no longer recognizable as stale and passes through instead of being dropped. Not evidenced to matter in practice — F52's own retry path (resending the suggested `codedom` snippet) is a new `tools/call` with a new id, never a reused one. Pinned by `test_execute_watchdog_id_reuse_after_fire_late_response_not_dropped`.

## Version-bump runbook (first-class deliverable, lives in the proxy repo)

Pin bump → re-capture canary baseline → diff tool list/schemas → re-run the repro driver (committed alongside) → re-verify the string-keyed behaviors (timeout strings, console-noise patterns) against upstream source → update baseline + strings in one commit. See `docs/bump-runbook.md`.

F22 keys on no string, so nothing there can go stale — but its **verdict** can, and it has **two independent halves**. The driver reports them separately: `F22-move-lies` (does upstream still report failure on a move that landed — GUID-verified, since a collision also leaves the destination present) and `F22b-bare-destination-relocates` (does a bare `destination` still resolve to `Assets/<name>` instead of beside the source). These are different mechanisms — verdict reporting versus argument resolution — so upstream can fix either alone. **Retire the refusal only when both read clean**; one clean half is not the criterion.
